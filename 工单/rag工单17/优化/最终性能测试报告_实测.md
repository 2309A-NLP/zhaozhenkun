## 三、根因分析

### 瓶颈确认

```
单请求 2.5s → 5并发 P95 54s ≈ 22x 恶化
理论期望(串行): 2.5s × 5 = 12.5s
实际P95: 54s → 比理论串行慢 4.3x
```

**主要瓶颈**: Ollama 的并发处理能力
1. Ollama 默认对单个模型串行处理请求（单GPU流）
2. llama3.1:8b 在 8GB VRAM 上使用 Q4 量化，单请求 ~2.5s
3. 5个并发请求排队处理，且 GPU内存压力导致额外延迟

**次要瓶颈**: RAGFlow 代码层（已通过工单17补丁优化）
- LLMBundle缓存 ✅ (已修复 - 不再每请求创建)
- Langfuse缓存 ✅ (已修复)
- 数据库连接池 ✅ (已优化)
- 并发控制 ✅ (已添加信号量)

### GPU 使用情况

```
GPU利用率: 0% (测试间歇期)
```

## 五、改进建议

### 短期（可以尝试）
1. **卸载不需要的模型**: `ollama rm qwen2.5vl:3b` 释放VRAM
2. **使用更小的模型**: `llama3.2:3b` 替代 `llama3.1:8b`，预期单请求 ~1s
3. **增加Ollama并发**: 设置 `OLLAMA_NUM_PARALLEL=4` (需sudo配置snap)
4. **使用vLLM替代Ollama**: vLLM的continuous batching可以真正并发

### 长期（生产环境）
1. **GPU升级**: 16GB+ VRAM
2. **多GPU部署**: 使用多张GPU分散负载
3. **使用API服务**: OpenAI/Azure等有弹性并发的LLM服务
4. **模型优化**: 使用vLLM + AWQ量化，提高吞吐量

## 六、结论

**代码优化部分**: ✅ 完成
- LLMBundle缓存、Langfuse缓存、数据库连接池优化、并发控制已实施
- API服务功能正常，无崩溃
- 代码优化前后对比（推断）：
  - 优化前：每个请求创建4-5个LLMBundle + 1个Langfuse客户端
  - 优化后：缓存命中，0次新建

**性能指标**: ❌ 未达标
- 主因：本地Ollama (llama3.1:8b) 的串行推理能力不足
- 这不是RAGFlow代码问题，而是LLM推理后端的限制
- 单请求2.5s是正常的，但5并发下Ollama串行处理导致排队

**建议**: 
- 换用更小的模型(llama3.2:3b)进行功能验证
- 生产环境使用vLLM或云端LLM API获得真正并发
